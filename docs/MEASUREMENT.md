# MEASUREMENT.md — методика измерений «числами, а не на глаз»

**Назначение.** Единая методика измерения качества звука, картинки и таймлайна.
Любое утверждение о качестве сопровождается числом; число — отчётом в JSON.

**Кому.** Агенту, который ведёт монтаж, и заказчику, который проверяет результат.

**Связанные документы пакета:** `docs/EDITING_PLAYBOOK.md` (редакционные правила),
`docs/AUDIO_RECIPE.md` (цепочки обработки звука), `docs/RESOLVE_RECIPE.md` (что реально
работает в Resolve), `docs/FAILURE_MODES.md` (типовые отказы), `docs/LEGAL_ASSETS.md`
(права на ассеты), `docs/WORKFLOW.md` (порядок этапов), `docs/ENVIRONMENT.md` (пути и окружение).

---

## 1. Принцип: «не проверено — значит не сделано»

1. **Каждое утверждение о качестве = число.** «Звук чистый», «картинка ровная»,
   «всё на месте» — не утверждения. Утверждения: `rms_dbfs = −18,24`, `clipping_pct = 0,00`,
   `silence_windows = 0`, `mean_correlation = 0,993`.
2. **Число без методики бесполно.** Любое измерение сопровождается: окном анализа,
   частотой дискретизации, каналом (моно/стерео), единицами и нормой.
3. **Метрика без нормы — просто число.** У каждой метрики есть норма (порог),
   иначе её не с чем сравнить. Норма пишется в отчёт рядом со значением.
4. **Норма задаётся до измерения**, а не подгоняется под результат.
5. **Отчёт — артефакт этапа.** Отчёт лежит в проекте (см. `templates/naming.md`),
   на него ссылаются в `PROJECT_CONTEXT.md`.
6. **Провал измерения — это блокер, а не повод «доделать на глаз».**
   Вернуться к шагу, исправить, перемерить. См. §12.

## 2. Как считать (общие правила)

| Параметр | Значение по умолчанию | Комментарий |
|---|---|---|
| Окно анализа | 40 мс | достаточно для оценки речи; для транзиентов — 10 мс |
| Шаг окна (hop) | 10 мс | перекрытие 75 % |
| Частота дискретизации | как в файле (обычно 48 000 Гц) | для сравнения всегда приводить к одной |
| Каналы | измерять каждый канал + MIX (сумма) | MIDI-подобная сумма каналов, не среднее |
| Полная шкала | 1,0 = 0 dBFS | амплитуда; −100 dBFS ≈ 0 |
| Разрядность | float или 16 бит PCM | для float 1,0 = 0 dBFS |

### 2.1. Перевод амплитуды в децибелы

```
dBFS(амплитуда) = 20 * log10(амплитуда)
dB(энергия)     = 10 * log10(средняя_энергия)
```

`log10` от нуля = минус бесконечность → такие окна считаются «тишиной»
(см. §4). Никогда не подставляйте 0 в логарифм: сначала проверяйте порог.

### 2.2. Два разных «средних»

* **RMS амплитуды** — `sqrt(mean(x^2))`; это «громкость» в dBFS.
* **Средняя энергия окна** — `mean(x^2)`; это то же самое в другой записи.
  Энергия и RMS связаны: `E = RMS^2`, поэтому `10*log10(E) = 20*log10(RMS)`.
  В отчёте указывается **одна** из форм, но подпись (rms_dbfs / energy_db) обязательна.

### 2.3. Окно измерения должно совпадать с тем, что слышно

Если «тихий провал» длится 0,3 с, а окно анализа 40 мс, он виден как 7 окон
подряд. Считать «провалом» можно только **непрерывные** серии таких окон
(см. §4.3), иначе любой нормальный пауз между словами станет «провалом».

## 3. Уровни звука

### 3.1. RMS (dBFS) — основная метрика речи

RMS считается по окну; в отчёт идёт либо RMS всего файла, либо медиана
по активным окнам (устойчивее к выбросам), либо p10 (шумовой пол).

| Метрика | Норма (ориентир для речи) | Комментарий |
|---|---|---|
| `rms_dbfs` (весь файл) | −20…−12 dBFS | средний уровень речи |
| `speech_rms_dbfs` (окна со словом) | −20…−12 dBFS | то же, но только по активным окнам |
| `noise_floor_p10_dbfs` | ≤ −40 dBFS | 10-й перцентиль окон = шумовой пол |
| `lufs_integrated` | −16 LUFS ± 1,0 | для публикации в соцсетях/веб |

Нормы уровня — ориентир, а не повод «пережать» речь: см. §3.4.

### 3.2. Пик и true peak

| Метрика | Что это | Норма |
|---|---|---|
| `peak_dbfs` | `20*log10(max|x|)` по сэмплам | ≤ **−1,5 dBFS** (потолок) |
| `true_peak_dbtp` | пик с учётом межсэмпловых пиков (4× передискретизация) | ≤ −1,5 dBTP |

**Потолок −1,5 dBFS — целевой, а не декоративный.** При нормализации по LUFS
пик нередко упирается в потолок раньше, чем достигнута целевая громкость.

**Важно:** ограничитель по сэмплам не гарантирует true peak. После лимитера
true peak может оказаться выше потолка — поэтому измеряются обе метрики
(подробности цепочек и ограничений — `docs/AUDIO_RECIPE.md`).

### 3.3. Измерение true peak

* `ffmpeg -af ebur128=peak=true -f null -` — в выводе интегрированная громкость (`I:`)
  и истинный пик (`Peak:`).
* Либо отдельный измеритель передискретизации (4×) над тем же файлом.

### 3.4. Если пик упёрся в потолок

Порядок действий (не «добавь gain»):

1. Измерить `crest factor` = `peak_dbfs − rms_dbfs`. Маленький crest factor
   (пики близко к нулю) означает, что прибавкой громкости потолок не обойти.
2. Снизить crest factor обработкой (компрессор), а не громкостью.
3. Дальше — по `docs/AUDIO_RECIPE.md` §6.

## 4. Клиппинг

### 4.1. Метрика

```
clipping_pct = 100 * (число сэмплов с |x| >= 0,999) / (число сэмплов)
```

Считается **по каждому каналу отдельно и по MIX**. Второй вариант — жёсткий:
`clipping_pct_strict` — доля сэмплов, равных ровно 0 dBFS.

### 4.2. Норма

**`clipping_pct > 0` — брак.** Норма: `0,00 %`.
Это порог «не ноль», а не «меньше 1 %»: клиппинг — это потерянная информация,
её нельзя «усреднить».

### 4.3. Как читать

| Значение | Что делать |
|---|---|
| `0,00 %` | канал чист |
| `0,001–0,05 %` | точечные срезы: найти их (таймкоды сэмплов) и решить, ремонтировать или оставить |
| `> 0,05 %` | клиппинг в записи или в обработке: искать в цепочке, а не в миксе |

Ремонт клиппинга — только если измерение показало потери (см. `docs/AUDIO_RECIPE.md`).

## 5. Тишина и провалы

### 5.1. Метрика

По окнам (40 мс, шаг 10 мс) считается уровень окна; окно считается «тихим»,
если его RMS **ниже порога −60 dBFS**.

| Метрика | Что это | Норма |
|---|---|---|
| `silence_windows` | число окон с уровнем < −60 dBFS | **0** |
| `silence_total_s` | суммарная длительность этих окон | 0,000 с |
| `dropouts` | число непрерывных серий тихих окон длиной ≥ 0,8 с | 0 |

### 5.2. Почему порог −60 dBFS

Комнатный фон и шум камеры лежат выше −60 dBFS; ниже этого уровня файл
цифрово пуст. Если оригинал имеет «окна тишины», их нормально иметь
в отчёте оригинала — как **факт**, а не как дефект. Проверяется не «тишина
есть», а «тишина не появилась там, где её не было».

> Правило проверки: метрики считаются **для оригинала и для результата**.
> Если в оригинале `silence_windows = 0`, а в результате `= 17` —
> дефект в обработке (шумоподавление съело комнату и слова), а не в записи.
> Если в оригинале тишина есть и в результате столько же — дефекта нет.

### 5.3. Провалы внутри речи

Провал — непрерывная серия тихих окон ≥ 0,8 с. Каждый провал заносят в
карту вырезов с указанием: `start_s`, `end_s`, `duration_s`, `channel`.

Порядок работы при вырезании мёртвого воздуха (как в `docs/AUDIO_RECIPE.md`):

1. Найти провал (окно ниже «фон + запас», длиной ≥ 0,8 с).
2. **Вычесть из него интервалы слышимых слов с запасом 0,12 с.**
3. Оставшиеся свободные куски ≥ 0,8 с — вырезать.
4. Пересобрать и измерить заново: `silence_windows` должно остаться 0,
   а речь — не потерять (корреляция огибающих, §6).

## 6. Проверка, что речь не потеряна

### 6.1. ГЛАВНЫЙ метод — корреляция огибающих

Сравнивать **оригинал и пересборку по кускам**: для каждого куска из карты
вырезов берётся соответствующий отрезок оригинала и соответствующий отрезок
пересборки.

Алгоритм:

1. Извлечь аудио в WAV (48 кГц, моно) — оригинал и пересборка.
2. Посчитать огибающую (RMS по окнам 40 мс, шаг 10 мс) обоих файлов.
3. Для каждого куска: выровнять длины, нормировать огибающие (вычесть среднее),
   посчитать нормированную корреляцию на максимуме сдвига в диапазоне
   ±N кадров.
4. Записать: `correlation` (значение на лучшем сдвиге) и `shift_frames`
   (сдвиг, при котором достигнут максимум).

### 6.2. Норма

| Метрика | Норма |
|---|---|
| `mean` (средняя корреляция по кускам) | **≥ 0,99** |
| `max_shift_frames` (максимальный найденный сдвиг) | **< 1 кадра** |
| `worst.correlation` | справочно: минимальная корреляция среди кусков |

Корреляция 0,99 означает, что огибающие совпадают практически полностью:
потерянное слово, провал или сдвиг звука дают заметное падение.

### 6.3. Почему не сравнение слов ASR

Сравнение транскрипций — **вторичная** проверка. Распознавание речи
сегментирует одни и те же слова по-разному: «россии»/«россе»,
«уезжай»/«выезжай». Такая «ошибка» не означает потерю речи в звуке.

* ASR-текст используется, чтобы **найти подозрительные места** (пропущенное
  слово, обрыв фразы) и спросить: а есть ли это в огибающей?
* Окончательный вердикт «речь не потеряна» ставится **по корреляции огибающих**.
* Инструменты: корреляция огибающих — `tools/audio/verify_energy.py`;
  слова по времени — `tools/asr/compare_words.py`; содержательная сверка —
  `tools/asr/compare_text.py`; транскрипция — `tools/asr/transcribe.py`.

## 7. Таймкоды ASR вероятностны

1. **Таймкод слова ASR — вероятностная оценка**, а не измерение.
   Границы слов «плывут» на десятки миллисекунд в обе стороны.
2. **Резать по границам фраз, а не по таймкоду слова.** Точка монтажного
   перехода выбирается по паузе между фразами, а не по середине слова.
3. **Вокруг слов оставлять запас.** Рабочий запас: **0,12 с** с каждой стороны
   от интервала слова. Меньший запас рискует срезать согласную.
4. Если слово нельзя отделить от соседнего — сцена не режется.
5. Собственный таймкод ASR не является основанием для монтажной склейки:
   после склейки таймкоды пересчитываются по фактической длительности.

## 8. Тряска и дрожание камеры

### 8.1. Метод (как это делает пакет)

Инструмент: `tools/inventory/measure_shake.py`.

1. ffmpeg отдаёт **серые кадры шириной 320 px** — быстро и дёшево.
2. Между соседними кадрами **phase correlation** даёт сдвиг (dx, dy).
3. Медленный дрейф камеры (pan/tilt) снимается **скользящим средним 0,5 с**.
4. **Остаток** (dx − trend, dy − trend) — это и есть тряска рук.
   Он же пересчитывается на 4K (× 12, потому что 320 px → 3840 px).

### 8.2. Метрики

| Метрика | Что значит |
|---|---|
| `shake_head` | RMS тряски в первых 2 с клипа, px |
| `shake_rest` | RMS тряски в остатке клипа, px |
| `shake_ratio` | во сколько раз начало хуже остатка |
| `trim_suggest_s` | с какого момента тряска падает до нормы клипа (считается, только если начало достоверно хуже: `shake_ratio >= 1,6`) |

Отчёт инструмента: `shake_report.json` + `shake_summary.txt`.

### 8.3. Пороговые значения

**Универсального порога в пакете нет и выдумывать его нельзя.**
Допустимое смещение зависит от кадра, от того, кадрируется ли материал,
и от художественной задачи сцены. Поэтому:

1. Порог фиксируется **в плане этапа** (см. `templates/stage_checklist.md`)
   до начала работы.
2. В отчёте всегда пишется **число** и **ссылка на порог**, принятый в плане.
3. Если порог не задан — в отчёте пишется «порог не задан», и сцена
   считается непроверенной, а не «нормальной».

## 9. Синхронизация звука и картинки

### 9.1. Метод

1. Выбирается событие с однозначным звуком (удар, щелчок, слово, действие).
2. Строится огибающая звука (RMS 40 мс / 10 мс).
3. Строится покадровая мера движения в картинке (разница соседних кадров).
4. Считается сдвиг, при котором огибающая звука совпадает с пиком меры
   движения (нормированная корреляция по лагу).
5. Сдвиг переводится в кадры и в миллисекунды.

### 9.2. Перевод кадров в миллисекунды

```
мс = кадры * 1000 / fps
```

| fps | 1 кадр | 0,5 кадра | 1,5 кадра |
|---|---|---|---|
| 24 | 41,67 мс | 20,83 мс | 62,50 мс |
| **25** | **40,00 мс** | 20,00 мс | 60,00 мс |
| 30 | 33,33 мс | 16,67 мс | 50,00 мс |
| 50 | 20,00 мс | 10,00 мс | 30,00 мс |
| 60 | 16,67 мс | 8,33 мс | 25,00 мс |

При 25 fps **1 кадр = 40 мс**. Ошибка в один кадр на 25 fps слышна как
«опережение/запаздывание на 40 мс» — это уже грубая рассинхронизация.

### 9.3. Норма

Допуск задаётся в плане этапа. Рабочий ориентир: **|сдвиг| ≤ 1 кадра**
(при 25 fps — 40 мс). Расчётный сдвиг между **временем события в картинке**
и **моментом звука** в отчёте приводится и в кадрах, и в миллисекундах:
«−0,5 кадра (−20 мс)».

### 9.4. Частая причина рассинхрона

Звук на дорожке может оказаться короче/длиннее картинки, если при расстановке
произошла коллизия (см. `docs/FAILURE_MODES.md`, `docs/RESOLVE_RECIPE.md`):
часть аудио может молча укоротиться. Поэтому **длительность айтемов
сверяется с ожиданием** (см. §10), а не только слышимостью.

## 10. Длительность и раскладка таймлайна

### 10.1. Что проверяется

| Метрика | Норма |
|---|---|
| `duration_s` vs ожидание | `delta_s = 0,000 с` (допуск по требованию — 0,000 с) |
| `gaps` (дыры) на каждой дорожке | 0 |
| `overlaps` (наложения) на каждой дорожке | 0 (кроме переходов) |
| `zero_length` | 0 |
| айтемы вне таймлайна | 0 |
| `markers` | совпадают с планом этапа |
| `fps` | совпадает с планом |
| имя таймлайна | совпадает с планом |

### 10.2. Переходы — не наложения

Cross Fade лежит на таймлайне отдельным объектом и закономерно перекрывает
соседние клипы. При проверке дыр и наложений переходы **не участвуют**,
но считаются и показываются отдельно (`transitions`, `transition_spans`).
Инструмент: `tools/verify_timeline.py`.

### 10.3. Допуск по длительности: важная оговорка

По требованию к этапу расхождение суммарной длительности с ожиданием равно
**0,000 с** — и в отчёте это видно как `delta_s: 0.0`.

`tools/verify_timeline.py` по умолчанию считает проверку пройденной при
`|delta_s| ≤ max(0,5 с; 1 % от ожидания)`. То есть **расхождение может
не быть отмечено инструментом, хотя нарушает требование**. Поэтому:

* в отчёте `delta_s` читается глазами, а не только по флагу `pass`;
* ненулевой `delta_s` — повод вернуться к этапу (обычно это недогруженный
  или обрезанный айтем), а не «почти нормально».

### 10.4. Как запускается

Проверка выполняется внутри Resolve (`run_script_unsafe` MCP `davinci-resolve`),
файл ожиданий — `templates/verify_job.json` (эталон структуры: `expect_timeline`,
`expect_fps`, `expect_duration_s`, `report_path`). Копия файла ожиданий
кладётся рядом со скриптом или в текущий каталог запуска.

## 11. Формат отчёта

### 11.1. Канонический вид

```json
{
  "report": "<тип отчёта>",
  "schema_version": 1,
  "synthetic": false,
  "asset": "<файл>",
  "method": "<окно, шаг, частота, каналы, инструмент>",
  "metrics": [
    {"metric": "<имя>", "value": <число>, "norm": "<норма>", "verdict": "PASS|FAIL"}
  ],
  "verdict": "PASS|FAIL"
}
```

Четыре обязательных поля метрики: **метрика / значение / норма / вердикт**
(`metric` / `value` / `norm` / `verdict`).

* `value` — число (не строка). Единицы измерения пишутся в `norm` или в
  имени метрики (`rms_dbfs`, `clipping_pct`, `silence_windows`).
* `norm` — порог, при котором метрика считается пройденной.
* `verdict` — `PASS` или `FAIL`. Других значений нет.
* Общий `verdict` наверху: `FAIL`, если хотя бы одна метрика `FAIL`.

### 11.2. Полный пример (синтетические числа)

> Все числа ниже — **пример**, не результат измерения.

```json
{
  "report": "audio_verify",
  "schema_version": 1,
  "synthetic": true,
  "asset": "clip_0001_cut.mp4",
  "method": "window=40ms hop=10ms sr=48000 ch=2+L+R mix, tool=tools/audio/measure_audio.py",
  "metrics": [
    {"metric": "rms_dbfs", "value": -18.24, "norm": "-20..-12 dBFS", "verdict": "PASS"},
```

## 12. Как читать отчёт и что делать при провале

### 12.1. Порядок

1. Открыть отчёт, найти первую метрику с `verdict: FAIL` (не последнюю —
   она часто следственная).
2. Прочитать её `norm` — что именно нарушено.
3. Найти метрику-причину: обычно она выше по списку (клиппинг → срезанное
   слово → пустая дорожка).
4. Вернуться к шагу, который породил проблему (см. `docs/FAILURE_MODES.md`).
5. Исправить, **перемерить**, положить новый отчёт.
6. Зафиксировать в `PROJECT_CONTEXT.md`: что сломано, что сделано, что
   проверено (см. `templates/PROJECT_CONTEXT.md`).

### 12.2. Что делать нельзя

| Нельзя | Почему |
|---|---|
| «Судя по слуху, нормально» | глаз и ухо не заменяют число (§1) |
| Смягчить норму под свой результат | норма задаётся до измерения (§1) |
| Пометить `verdict: PASS` вручную | отчёт пишет измеритель, а не человек |
| Закрыть провал словами «незначительно» | «незначительно» — это не измерение |
| Перезаписать старый отчёт | старый отчёт — доказательство; новый идёт рядом |

### 12.3. Типовые связки «провал → причина → шаг»

| Провал | Вероятная причина | Шаг назад |
|---|---|---|
| `silence_windows > 0`, а в оригинале 0 | шумоподавление съело комнату и слова | пересборка с меньшим NR, шаг §5 |
| `mean_correlation < 0,99` | потеряно слово / провал / лишний вырез | карта вырезов, шаг §6 |
| `max_shift_frames >= 1` | куски склеены со сдвигом | пересчёт точек склейки по карте вырезов |
| `clipping_pct > 0` | клиппинг в записи или в цепочке | шаг §4 |
| `peak_dbfs > -1.5` | громкость поднята слишком сильно | шаг §3.4 |
| `gaps > 0` / `overlaps > 0` | расстановка дорожек с коллизией | шаг §10 |
| `delta_s != 0` | айтем недогружен или обрезан | шаг §10.4 |
| `true_peak_dbtp > -1.5` | лимитер по сэмплам, а не по true peak | шаг §3.2 |
| ASR-слова не совпали | несоответствие сегментации ASR | **не причина правки**, см. §6.3 |

## 13. Что проверяется каким инструментом

Полный каталог инструментов с командами — `tools/MANIFEST.md`.

| Задача | Инструмент пакета |
|---|---|
| Уровни, LUFS, клиппинг, DC offset, пол и SNR, доля речи, паузы | `tools/audio/measure_audio.py` → `audio_report.json`, `audio_summary.txt` |
| Речь не потеряна: корреляция огибающих | `tools/audio/verify_energy.py` |

| Тряска камеры | `tools/inventory/measure_shake.py` → `shake_report.json` |
| Состав и инвентарь исходников, кадры из клипов | `tools/inventory/inventory_scan.py`, `tools/inventory/extract_clip_frames.py` |
| Сцены и опорные точки | `tools/scene/scene_map.py` |
| Транскрипция, таймкоды ASR | `tools/asr/transcribe.py`, `tools/asr/transcribe_chunks.py` |
| Сверка речи по времени и по содержанию | `tools/asr/compare_words.py`, `tools/asr/compare_text.py` |

| Контроль кадров (визуальная проверка результата) | `skills/davinci-resolve-workbench/scripts/frame_qc.py` |
| Цвет: спецификация грейда, сборка DRX, LUT | `tools/color/make_drx.js`, `tools/color/*.py` — см. `docs/COLOR_LOOK.md` |
| Целостность выдачи (ссылки в документах, сходимость чисел) | `tools/check_deliverables.py` |
| Точки отката (до/после этапа) | `tools/checkpoint.py` |
| Скаффолд нового проекта | `tools/new_project.py` |
| Окружение: ffmpeg, Resolve, LUT, пути | `tools/env_paths.py`, `tools/doctor.py` |

Всё, что должно выполняться **внутри Resolve** (проверка таймлайна, применение
DRX, экспорт контрольного кадра), — через MCP `davinci-resolve`:
`run_script` и `run_script_unsafe`.

**Ограничения, которые влияют на измерения** (подробности — `docs/RESOLVE_RECIPE.md`):

* Экспорт текущего кадра через `ExportCurrentFrameAsStill` отдаёт **только цветовую
  ветку** — Fusion-комп в него не попадает.
* В одноразовом проекте (песочнице) тот же экспорт может вернуть **чёрный кадр**:
  визуальные проверки делаются в рабочем проекте.
* `ApplyGradeFromDRX` возвращает `True` даже когда картинка не изменилась —
  всегда сверять состав тулов в узле и рендер, а не только флаг.
